# Tender Reuse: Answer an RFQ From Past Lines and Modules

> **A bid needs a deviation list the customer can sign, not a similarity score.**

Runnable SQL for a bid engineer who checks a customer's specification (Lastenheft) against the
machines the company has built before and against its module catalogue. The result is a
ranking, a must-clause view, and a deviation list with clause number, page and must/should.

## The Story

**Who.** The bid engineer of Allgäuer Abfülltechnik Demo GmbH, a builder of cup filling and
sealing lines (fictional company, people and part numbers).

**Trigger.** RFQ-2026-014 from Molkerei Bergblick Demo eG (fictional): a yoghurt-cup filling and
sealing line. The German document has 42 clauses on pages 14 to 61, 37 of them *must* and 5
*should*, plus an English annex for the labeller. The offer is due in two weeks.

**Decision.** Which past line is the bid basis, which clauses it does not meet (that list goes
to the customer with the offer), and which stations can be built from catalogue modules instead
of engineering hours.

## Functions

| Function | Used for |
|----------|----------|
| `tree_from_json` | Load the extracted RFQ document, parse every value in German |
| `parse_quantity`, `quantity_units`, `normalize_quantity` | Parse audit, custom unit "Becher/min", base units in the archive export |
| `validate_trees`, `tree_anchors` | Find duplicates and categories without a dimension; resolve the class of an unnamed item |
| `tree_coverage`, `tree_coverage_trace` | Rank the past lines; explain each clause |
| `value_satisfies` | Strict re-check of every value with no tolerance |

## Quick Start

```bash
# From the repository root
DATAZOO_DISABLE_TELEMETRY=1 ./build/release/duckdb < examples/tender_reuse/01_load_and_audit.sql
DATAZOO_DISABLE_TELEMETRY=1 ./build/release/duckdb < examples/tender_reuse/02_rank_past_lines.sql
DATAZOO_DISABLE_TELEMETRY=1 ./build/release/duckdb < examples/tender_reuse/03_deviations_and_modules.sql

# Check every printed number against the comments
scripts/run_examples.sh tender_reuse
```

Every script loads its own data with the same block, so each one runs alone. The block names
four inputs and every coverage call uses three settings:

| Input | Table | Why |
|-------|-------|-----|
| The request | `rfq_nodes`, `rfq_attributes` | From the extracted JSON with `tree_from_json`, values parsed in German |
| The archive | `past_line_nodes`, `past_line_attributes` | PLM export of 12 past lines, values in base units |
| The clause sidecar | `clauses` | `clause_id, page, must_should, kind, node_id, attr_id, text`: what the tree does not carry |
| The house glossary | `vocabulary_overrides` | "Kompaktaggregat Hygiene" is a CIP unit, not a hygiene enclosure |

| Setting | Why |
|---------|-----|
| `mu := 0.0` | Compare values only. Attribute names in the archive are German, English or typo'd; with the default, English names alone cost 0.17 of coverage |
| `default_bounds := 'catalogue'` | "72 dB(A)" has no bound word. The catalogue template says `at_most`, otherwise it would mean "exactly 72" |
| `rules_table := 'compatibility_rules'` | IP67 meets "IP65 oder besser", PN25 meets "PN 16"; a lower class never does |

## What to Look At

**01: trust the parse before the score.** All 27 value clauses are read with a dimension or
category (step 2). Three of four designation clauses are refused (all NULL), which is what you
want; `Werkstoff produktberührt 1.4404` is still read as the count 1.4404 (step 4), so manual
clauses are kept out of the tree by the sidecar's `kind`. `validate_trees` flags the three
category clauses without a dimension and the duplicated row; it does not flag the length in mm,
which step 6 finds against `quantity_units()`.

**02: the bid view.** Five lines miss no must clause; every line misses C-42 (should):

| candidate_id | coverage | rank | must_missed | should_missed | must_coverage |
|--------------|---------:|-----:|------------:|--------------:|--------------:|
| PAST-LEAN-2019 | 0.9697 | 1 | 0 | 1 | 1.0 |
| PAST-SWAP-2018 | 0.9697 | 2 | 0 | 1 | 1.0 |
| PAST-UNIT-2021 | 0.9697 | 3 | 0 | 1 | 1.0 |
| PAST-RICH-2022 | 0.9697 | 5 | 0 | 1 | 1.0 |
| PAST-FAST-2024 | 0.8788 | 11 | 0 | 4 | 1.0 |
| PAST-TOL-2023 | 0.9576 | 5 | 2 | 1 | 0.9394 |

PAST-TOL-2023 ranks 5th on coverage but misses two must clauses, and PAST-FAST-2024 ranks 11th
only because it has no (optional) labeller. Coverage is a ranking aid; `must_missed` decides.
Step 2 shows what each setting is worth on three full-cover lines (0.858 → 0.9697 for the bid
basis); step 3 shows PAST-SWAP-2018's drives paired by value (90 W clause ↔ 95 W drive); step 5
scores the deviations against `gold_deviations.csv`: the kernel finds 32 of 33 with the default
tolerance and all 33 with `tol := 0, soft_band := 0`, as does the per-clause re-check; no false
positives.

**03: what goes to the customer.** The deviation list for PAST-LEAN-2019 is five rows: four
clauses to confirm by hand and C-42 (1 200 instead of 1 400 cups/min). Offered values print in
the clause's unit (80 °C, 1200 Becher/min), not in base units. Modules: MOD-CIP.V1, MOD-DOSE.V3
and MOD-SEAL.V2 cover their stations alone, which agrees with `gold_station_cover.csv`; no
variant covers the cup feed, so that station needs engineering.

## Known Limits and Workarounds

| Limit | Effect here | Workaround in this folder |
|-------|-------------|---------------------------|
| The default tolerance (`tol` 0.02 plus `soft_band`) passes near misses | 7.6 A against "höchstens 7,5 A" scores 1.0 | `tol := 0, soft_band := 0` on `tree_coverage(_trace)` for a signable list; `clause_check` re-checks per clause with `value_satisfies(..., NULL, 0.0, 0.0)` |
| `is_gap` marks a whole requirement item | A met attribute next to a missed one shows `is_gap = true` | Verdicts use `value_score` per attribute and the counts per item |
| Trace values are in base units | 353.15 K, 20 Hz, 9000000 s in `req_value` / `prov_value` | Re-parse the clause for `source_unit` and convert with `quantity_units()` |
| The kernel reads candidate values as base units | 10500 mm is read as 10500 m and fails "max. 12 m" | `normalize_quantity` at load |
| A category from text has no dimension | `validate_trees` warns `category_without_dimension` | Regex normaliser at load: `IP…` → protection_class, `PN…` → pressure_class |
| OR alternatives are chosen per requirement item | A module tree "covers" a station with parts of two variants | Score each variant as its own tree (03, step 3) |
| No must/should weighting in the kernel | Coverage mixes must and should | The clause sidecar and `must_missed` / `must_coverage` in SQL |
| Material numbers such as `1.4404` parse as counts | A designation would be compared as the number 1.4404 | `kind = 'manual'` in the sidecar keeps them out of the tree |
| Table functions take literal parameters only | `candidates := (SELECT list(...))` is an error | `k := 10` over a candidate table holding only the variants |

The extraction from PDF to JSON is assumed done; `clauses.csv` is maintained by the bid
engineer next to it. Inferred deviations are a draft for the bid engineer, not a compliance
statement.
