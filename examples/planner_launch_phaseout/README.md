# Launch, Phase-Out and Shortage Planning

> **A lookalike BOM is not a forecast basis until its history is dense, and a set match is not a substitute until the quantities fit.**

Runnable SQL for a demand planner who prepares a product launch and a component cut-over from a
BOM export and goods movements. The results are investigation lists for the planning meeting:
a history analog, a predecessor candidate, the stranded components and a shortage alternative.
They are not forecasts and not substitute approvals.

## The Story

**Who.** The demand planner of VoltEdge (fictional company and part numbers), a maker of chargers
and cables.

**Trigger.** Two changes land in the same planning cycle. The black 65 W charger
`CHARGER-65W-EU-BLACK` launches with no sales history of its own. The USB cable
`CABLE-USB2-1M-V2` has replaced `CABLE-USB2-1M-V1`, but nobody maintained the supersession in
the material master. And a component of the new charger is short.

**Decision.**

1. Which existing charger's consumption is the starting point for the BLACK forecast?
2. Which material did the V2 cable replace, and which V1 components are left without a use?
3. If BLACK cannot be built, which existing BOM covers its component quantities best, and what
   is missing?

## Functions

| Function | Used for |
|----------|----------|
| `cold_start_analogs` | History analogs for the new charger, raw and on a dense-issue view |
| `infer_predecessors` | The built-in predecessor search for V2 (finds nothing here) |
| `find_similar_materials_jaccard` | BOM overlap for the cut-over recipe; set similarity for the shortage |
| `bom_where_used`, `bom_common_components` | Installed-base impact of a component; shared parts of V1 and V2 |
| `find_covering_entities` | Quantity-aware containment: how much of BLACK's component quantity a BOM covers |

## Quick Start

```bash
# From the repository root
DATAZOO_DISABLE_TELEMETRY=1 ./build/release/duckdb < examples/planner_launch_phaseout/01_launch_analogs.sql
DATAZOO_DISABLE_TELEMETRY=1 ./build/release/duckdb < examples/planner_launch_phaseout/02_cutover_shortage.sql

# Check every printed number against the comments
scripts/run_examples.sh planner_launch_phaseout
```

Each script loads its own data, so each one runs alone. Both build the same table from the
BOM export:

| Table / view | Built from | Why |
|--------------|------------|-----|
| `bom_items` | `bom_edges.csv.gz`, grouped by parent and child with `sum(quantity)` | 36 BOM positions are split over two rows; they must be added, not deduplicated |
| `issues_only` (02) | movements with type `261` and quantity > 0 | Returns and receipts are not consumption |
| `issue_density`, `dense_issues` (01) | issues per material, with at least 20 active weeks | Calendar span alone lets a two-posting material through |
| `component_features` (02) | `bom_items` renamed to `entity_id, feature_id, weight` | Input of `find_covering_entities`, over all 60 parents |

## The Data

Generated by `scripts/src/scripts/examples/planner_launch_phaseout.py` (fixed seed, sorted
rows, byte-identical gzip output):

```bash
cd scripts && uv run python -m scripts.examples.planner_launch_phaseout
```

| File | Rows | Columns / content |
|------|-----:|-------------------|
| `bom_edges.csv.gz` | 936 | `parent_id, child_id, quantity`: 60 parents with 15 components each, 900 unique positions, 36 of them split over two rows |
| `movements.csv.gz` | 8,539 | `material_id, movement_date, movement_type, quantity`: weekly postings 2023-01-02 to 2025-12-22 for 59 materials (BLACK has none); 7,874 issues (`261`), 140 returns (`262`, negative), 525 receipts (`101`) |
| `gold_planner.csv.gz` | 3 | `case_id, expected_material_id, reason`: the reviewed answer for `cold_start`, `cutover` and `shortage` |

The 60 parents are the four 65 W chargers, the two cables and 54 modules (`VE-MODULE-000` to
`-053`). The modules share no component with the chargers or the cables; they are the rest of
the BOM base that every search has to look through.

### Planted traps

| Trap | Where | What happens |
|------|-------|--------------|
| Sparse lookalike | `CHARGER-65W-EU-GREY`: 14 of BLACK's 15 components, 2 issues of 1 piece, 2023-01-02 and 2025-11-17 | `history_months` is 34, so it passes `min_history_months := 12` and ranks first by similarity. It has 2 active weeks |
| Returns-only material | `CHARGER-65W-EU-RETURN`: 120 postings, all type `262` | 27 history months from returns alone; ranks second as a raw analog |
| Dense analog | `CHARGER-65W-EU-WHITE`: 156 active issue weeks, mixed with returns and receipts | The right analog, but only third by similarity (12 shared components) |
| Duplicate BOM positions | 36 modules: the first component is `1 + 1` rows | `sum(quantity)` gives the 900 positions with the right quantity; `DISTINCT` would halve them |
| Clean cut-over | V1 issued weekly until 2024-06-24, V2 from 2024-07-01, about 100 a week each | No overlap and no ramp, so there is no anti-correlated demand for `infer_predecessors` to find |
| Stranded components | `VE-COMP-039` to `VE-COMP-044` | In V1 only; not used by V2 or any other parent |
| Quantity versus set | GREY uses 0.5 of each component, WHITE 3, BLACK 1 or 2 (18 in total) | GREY has the highest set Jaccard but covers only 7 of 18 units |

## What to Look At

**01: density before similarity.** The raw `cold_start_analogs` call ranks GREY first:

| material_id | similarity | history_months | active issue weeks |
|-------------|-----------:|---------------:|-------------------:|
| CHARGER-65W-EU-GREY | 0.875 | 34 | 2 |
| CHARGER-65W-EU-RETURN | 0.7647 | 27 | 0 (returns only) |
| CHARGER-65W-EU-WHITE | 0.6667 | 35 | 156 |

On the `dense_issues` view (positive `261` issues, at least 20 active weeks) only WHITE remains,
with similarity 0.6667 and 35 history months. That matches `gold_planner.csv.gz`.

**02, steps 2 to 4: the cut-over.** `infer_predecessors('CABLE-USB2-1M-V2')` returns 0 rows.
With `min_confidence := 0` it does return V1, at confidence 0.3556 (correlation -0.0601,
similarity 0.4286, temporal score 0.6767), below the default threshold of 0.5: a clean switch has
no anti-correlated overlap. The recipe in step 3 pairs BOM overlap with the last issue before
V2's first issue and finds V1: Jaccard 0.4286, last issue 2024-06-24, 7 days before the launch.
That is a candidate for the catalogue team, not proof of supersession.

**02, step 5: impact.** The constrained component `VE-COMP-000` is used in 4 parents (the four
chargers). V1 and V2 share 9 components; 6 are in V1 only, and `VE-COMP-043` is installed in 1
parent (V1), so it has no use after the phase-out.

**02, step 6: the shortage.** Both searches run over all 60 parents. Only the three other
chargers share a component with BLACK, so they are the only candidates with a score above zero;
the 54 modules and the cables do not compete.

| material | Jaccard (set) | shared components | quantity containment | shared / required units |
|----------|--------------:|------------------:|---------------------:|------------------------:|
| CHARGER-65W-EU-GREY | 0.875 | 14 | 0.3889 | 7 / 18 |
| CHARGER-65W-EU-RETURN | 0.7647 | 13 | 0.7222 | 13 / 18 |
| CHARGER-65W-EU-WHITE | 0.6667 | 12 | 0.7778 | 14 / 18 |

Set Jaccard picks GREY; quantity containment picks WHITE, which agrees with gold. WHITE still
lacks 3 of BLACK's 15 components (4 of 18 units) and uses 3 of each part it has, so 0.7778 is a
shortlist position for engineering and procurement, not a substitute release. RETURN is close
behind on BOM, but it has no issue history.

## Known Limits and Workarounds

| Limit | Effect here | Workaround in this folder | Proper fix |
|-------|-------------|---------------------------|------------|
| `cold_start_analogs` measures history as the calendar span between postings, of any movement type | GREY (2 issues) and RETURN (returns only) outrank WHITE | `-- BRIDGE` in 01, step 2: `issue_density` counts active issue weeks per material | An `active_weeks` output column and threshold in `cold_start_analogs` |
| `cold_start_analogs` reads every row of `movements_table` | Returns and receipts count as history | `-- BRIDGE` in 01, step 4: `dense_issues` keeps positive `261` issues with at least 20 active weeks | A movement-type and density filter in the API |
| `infer_predecessors` needs anti-correlated demand (default `min_confidence` 0.5) | A clean cut-over scores 0.3556 and is dropped | `-- BRIDGE` in 02, step 3: Jaccard plus a 12-week window before the successor's first issue | A cut-over signal (last issue just before first issue) in `infer_predecessors` |
| `infer_predecessors` considers only the 100 materials with the most similar BOMs | No effect in 60 parents; in a base with many near-identical variants the predecessor can fall outside | The step 3 recipe has no such cap; raise its `k` | See [the predecessors guide](../../docs/guides/03-predecessors-and-cold-start.md) |
| `find_similar_materials_jaccard` returns materials with no shared component (similarity 0) to fill `k` | With `k = 5` the two cables appear at 0.0 | `min_similarity := 0.01` in 02, step 6 | Documented behaviour; filter in SQL |
| Set similarity ignores quantities | GREY ranks first while covering 7 of 18 units | `find_covering_entities` on the BOM as a weighted feature table | It can also read `bom_items` directly with `entity_col := 'parent_id', feature_col := 'child_id', weight_col := 'quantity'` |
| No stock, open orders or effectivity dates in the inputs | Coverage says nothing about what can be built this week | Out of scope | Join your own stock and order data after the ranking |

The gold file records the reviewed answer for each decision; it is written by the generator,
independently of the extension.
