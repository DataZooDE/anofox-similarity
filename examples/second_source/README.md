# Second Source for Cast Parts

> **A foundry closes. Which approved foundry can make each of its parts, and which parts need a new supplier?**

A runnable scenario on fictional data: parts and suppliers are matched by capability class, with
quantities, a rules table, the coverage kernel and its trace. It runs on non-BOM data.

## The Story

- **Who:** the category manager for castings at a fictional pump and valve maker.
- **Trigger:** Hartmann Gusstechnik (`SUP-HART`) announces that its iron foundry closes next
  quarter. 40 active cast parts are single-sourced there.
- **Question:** for each part, which approved foundries meet every requirement on the drawing?
  Which parts does nobody cover?
- **Decision:** which RFQs go out this week and to whom (up to three foundries per part), and
  which parts start a new supplier search. The CPO wants the risk list by Friday.

The drawing extract (German and English) states weight, raw-part envelope, material grade,
pressure test, inspection certificate, lot size, surface roughness and general tolerance. Each
foundry has a capability sheet with the same kinds of values, written its own way.

## Data

Everything is in [`data/`](data/) and fictional. It is generated by
`scripts/src/scripts/examples/second_source.py` (fixed seed, byte-identical output):

```bash
cd scripts && uv run python -m scripts.examples.second_source
```

| File | Rows | Columns |
|------|------|---------|
| `parts.csv` | 40 | `part_id, description, material_group, current_supplier_id, annual_qty` |
| `part_requirements.csv` | 231 | `part_id, req_id, attr_name, value_text, lang` (the drawing extract) |
| `suppliers.csv` | 15 | `supplier_id, name, country, status` (`approved`, `not_approved`, `exiting`) |
| `supplier_capabilities.csv` | 111 | `supplier_id, capability, value_text, lang` (the capability sheets) |
| `capability_classes.csv` | 10 | `class_id, kind, dimension, bound, ladder, description` |
| `attribute_vocabulary.csv` | 34 | `wording, side, class_id` (DE and EN wordings → class) |
| `compatibility_rules.csv` | 9 | `dimension, required, provided, score`: PN10 < PN16 < PN25 < PN40 (6 rows), EN 10204 2.2 < 3.1 < 3.2 (3 rows) |
| `gold_second_source.csv` | 480 | `part_id, supplier_id, covers, failing_classes` for 40 parts × 12 approved foundries |

`capability_classes` is the master data that carries the design:

- **kind:** `numeric` values go through `parse_quantity`. `category` values (grades, PN,
  certificates) never do; SQL normalisers in the loader read them.
- **bound:** the direction a requirement of this class needs (the foundry's maximum weight must
  be *at least* the part weight; its achievable Ra *at most* the drawing's Ra). It overrides the
  wording on the drawing.
- **dimension:** for categories, the key into `compatibility_rules`.

The gold file is computed by the generator from the clean values with strict limits. It does not
depend on the extension.

## Running

From the repository root:

```bash
DATAZOO_DISABLE_TELEMETRY=1 ./build/release/duckdb < examples/second_source/01_parse_audit.sql
DATAZOO_DISABLE_TELEMETRY=1 ./build/release/duckdb < examples/second_source/02_rank_and_score.sql

# both, with the expected numbers checked
scripts/run_examples.sh second_source
```

Both scripts read the shared loader [`sql/load.sql`](sql/load.sql) with `.read`; it prints nothing.

| Script | What it does |
|--------|--------------|
| [`sql/load.sql`](sql/load.sql) | raw files → vendor dedup → class per row → values (numbers parsed, codes normalised) → one tree per part and per supplier, one item per capability class |
| [`01_parse_audit.sql`](01_parse_audit.sql) | row counts, wordings without a class, what `parse_quantity` makes of codes, the normalisers on the traps, units, direction overrides, gates, vendor dedup |
| [`02_rank_and_score.sql`](02_rank_and_score.sql) | `tree_coverage` for all 40 parts at once, gap list from `tree_coverage_trace`, hard limits, headline, RFQ list, new-supplier list, score against gold, what the vendor filters prevent |

## What to Look At

- **One item per capability class.** The kernel compares a required attribute with the best
  provided attribute *of the same dimension* on the matched item; names only discount. Roughness,
  tolerance and envelope are all lengths, so on one item a foundry's 3.2 µm roughness could
  "meet" a part's ± 0.05 mm tolerance. With one item per class, the class decides which values
  meet. `n_gaps` then counts failing classes.
- **The headline (02, section 4):** 37 parts reach coverage ≥ 0.9, 34 have a full cover by the
  kernel, 33 under hard limits, 7 need a new supplier. Coverage is a ranking score.
  For an RFQ use `n_gaps = 0` under hard limits.
- **Hard limits (02, section 3).** With the default tolerance `tree_coverage` scores values up
  to 2 % outside a limit (4.7 % for masses, which use a log scale) as met; the trace shows them
  as `value_score` 1 with `distance > 0`. The RFQ ranking passes `tol := 0, soft_band := 0`, so
  the 37 kg pour and the 650 mm part in a 600 mm flask become gaps.
- **The score (02, section 6):** recall@3 = 1.0 with and without hard limits. Hard limits
  take the precision of the listed sources from 0.988 to 1.0 and finds the 7th part with no
  source.
- **The filters (02, section 7):** without the approval filter all 40 parts look sourced
  (Novaguss is in 19 top-3 lists). Without the vendor dedup, Brandt takes two of the three RFQ
  slots on 21 parts.

## Known Limits and Workarounds

| Limit | Workaround here |
|-------|-----------------|
| The default tolerance of `tree_coverage` (`tol` 0.02, `soft_band` 0.05) passes near misses | `tol := 0, soft_band := 0` for the RFQ ranking |
| A bound stated in the text always wins over `default_bound` / `default_bounds := 'catalogue'`, but drawing wording describes the part, not the capability | the loader writes `bound` from `capability_classes` and keeps the parsed bound only for the audit |
| `parse_quantity` refuses certificate texts, but `3.1 acc. to EN 10204` is 3.1 with unit `acc` | certificates are read with a regex, never parsed |
| No range of categories (`GJS-400 … GJS-700`) | expanded to one value per standard grade (the kernel takes the best) |
| A category without a dimension | `validate_trees` warns (`category_without_dimension`); `01`, section 7 also gates on it |
| Envelope as a box fit | three sorted `at_least` classes. Allows axis-aligned rotation; does not model core prints or draft |
| Grades are nominal: GJS-500 does not stand in for GJS-400 | engineering approval outside this example; add a rule only if materials engineering signs it |
| Hardness, heat treatment and anything not in the vocabulary is not checked | listed in `01`, section 2 for a manual check |
| The RFQ list sorts full covers by stage-1 fit, not by price, distance or capacity | join your own supplier scores after `rfq_list` |
