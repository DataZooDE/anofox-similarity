# AAS Capability Matching

> **A request and four supplier answers arrive as Asset Administration Shells. Which offer meets the
> IDTA-02020 Required capabilities, what is missing, and how does the answer go back as AAS?**

A runnable scenario on fictional data: AAS JSON, XML and an AASX package are read into property
trees, matched by dictionary key with the coverage kernel, explained, written back as AAS, and a
supplier without semanticIds is enriched with a review step.

## The Story

- **Who:** the buyer for drive technology at a fictional packaging-machine builder, Kröger
  Verpackungstechnik, and its data steward.
- **Trigger:** RFQ 2026-117 asks for a servo drive for the Y axis of a tray sealer. The RFQ is an
  AAS with IDTA-02020 *Required* capabilities: position-controlled motion (rated current at least
  7.6 A, supply 380–480 V, ambient at least 45 °C, safe torque off) and fieldbus communication
  (EtherCAT, cycle time at most 1 ms).
- **Question:** which of the four answers (Lenvaro, Driventa, Kessler, Orbitec) meets the RFQ, and
  which property fails for the others? A later supplier, Nordwerk, sends an AAS without any
  semanticIds.
- **Decision:** award Lenvaro, ask Kessler for the two values it could not state, and code Nordwerk's
  properties once so it can be compared from then on.

## Data

Everything is in [`data/`](data/) and fictional. It is generated by
`scripts/src/scripts/examples/aas_capability_matching.py` (byte-identical output):

```bash
cd scripts && uv run python -m scripts.examples.aas_capability_matching
```

| File | What |
|------|------|
| `rfq_2026_117.aas.json` | the RFQ: one shell, IDTA-02020 Required capabilities |
| `offers/lenvaro_lx8.aas.json` | AAS JSON: TechnicalData and Offered capabilities |
| `offers/driventa_ds12.aas.xml` | AAS XML |
| `offers/kessler_ksd10.aasx` | an AASX package with XML inside, like the official IDTA packages |
| `offers/orbitec_ox6.aas.json` | AAS JSON with a SubmodelElementList of protocols |
| `formats/` | the Lenvaro offer as JSON, XML and AASX (the same trees) |
| `eclass_units.csv` | stand-in for a licensed unit list: symbol → ECLASS unit IRDI |
| `gold_offer_verdicts.csv` | 24 verdicts (offer × required property), from the clean values |
| `sealing/` | a ComposedOf sealing station, two offers and a capability taxonomy (GeneralizedBy) |
| `io_profile/` | a remote I/O station with three configurations and channel counts ([AAS profile](../../docs/guides/10-aas-profile.md)), with and without the profile |
| `enrichment/` | Nordwerk's uncoded AAS, uncoded names and dictionary phrasings with vectors, gold ids |

The IRDIs follow ECLASS syntax but are illustrative: no ECLASS content is reproduced. Vectors are
hashed character trigrams, a deterministic stand-in for the sentence encoder you would bring.

### Planted traps

| Trap | Where | What the example shows |
|------|-------|------------------------|
| A *peak* current whose IRDI shares tokens with the *rated* current | Driventa | `key_mismatch`, shown with its 12 A, not partial credit (`02`) |
| The rated current from an older ECLASS release (#007), the voltage as ECLASS IRI, the unit as UN/ECE code `AMP` | Lenvaro | matched by `semantic_key`; `n_mixed_releases` in the quality report (`01`) |
| A value with a semanticId but no ConceptDescription; a cycle time of `n/a` | Kessler | `missing_concept_description`, `bad_value`; trace `gate` / `missing` (`01`, `02`) |
| An unknown unitId with the unit text `A` as fallback; `6,0` in an `xs:double`; protocols as a list | Orbitec | `unknown_unit_id`, `decimal_comma`, a multi-valued property (`01`) |
| `Gewicht` (weight), nothing in the dictionary fits | Nordwerk | `fits = false`: p1 alone would have said 0.999 (`04`) |

## Run

From the repository root:

```bash
DATAZOO_DISABLE_TELEMETRY=1 ./build/release/duckdb < examples/aas_capability_matching/01_load_and_audit.sql
DATAZOO_DISABLE_TELEMETRY=1 ./build/release/duckdb < examples/aas_capability_matching/02_rank_offers.sql
DATAZOO_DISABLE_TELEMETRY=1 ./build/release/duckdb < examples/aas_capability_matching/03_write_back_as_aas.sql
DATAZOO_DISABLE_TELEMETRY=1 ./build/release/duckdb < examples/aas_capability_matching/04_enrich_uncoded_supplier.sql
```

| Script | What it does |
|--------|--------------|
| `01_load_and_audit.sql` | audit with `aas_issues`, load with `aas_to_trees`, `validate_trees`, `aas_quality` |
| `02_rank_offers.sql` | `tree_coverage`, the gap list from `tree_coverage_trace`, 24/24 against gold, `attrs_satisfying` |
| `03_write_back_as_aas.sql` | `aas_export` (round trip), `aas_coverage_result` |
| `04_enrich_uncoded_supplier.sql` | `aas_quality`, `suggest_semantic_id`, `apply_vocabulary_review`, matching by key |

The sealing station (composition, class hierarchy) and the I/O profile (variants, counts) are
covered by `test/sql/aas/uc_05` and `uc_06`; the API page has their queries.
